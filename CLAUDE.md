## Architecture

This is a Next.js App Router project styled with Tailwind CSS v4 and shadcn/ui. Its one feature is an AI-generated dictionary: a search box (`components/dictionary-search.tsx`, rendered from `app/page.tsx`) calls `app/api/define/route.ts`, which returns a definition generated by Gemini Flash Lite, cached in Firestore.

**Next.js version is non-standard.** See `AGENTS.md` (imported above) — this is not the Next.js version in your training data. Check `node_modules/next/dist/docs/` for the real API before using App Router conventions you already "know" (routing, layouts, metadata, etc.). Note: `app/api/define/route.ts` deliberately uses the Web-standard `Request`/`Response` APIs rather than `NextRequest`/`NextResponse`, to sidestep any drift in Next-specific request typing in this version. Concrete example this bit: this version deprecates `middleware.ts`/the Edge runtime in favor of **`proxy.ts`**, running on the Node.js runtime — see Authentication below.

### Authentication

The whole app requires sign-in (Google only) — see `specs/authentication.md` for the full design. Two separate mechanisms, don't confuse them:

- **`lib/firebase-client.ts`** — the client-side Firebase singleton (`auth`, `db`, `googleProvider`), from `NEXT_PUBLIC_FIREBASE_*` env vars. The app's first client-side Firebase usage (previously only the Admin SDK existed, server-side).
- **`lib/use-auth.ts`** — `useAuth()` wraps `onAuthStateChanged` (`{ user, isLoading }`); `signInWithGoogle()`/`signOutUser()` are plain exported functions, not hook-returned.
- **`proxy.ts`** (project root) — gates page navigation. Runs on the Node.js runtime (this Next version's replacement for `middleware.ts`/Edge), which is what makes it safe to call `firebase-admin` directly here for real cryptographic session-cookie verification (`auth.verifySessionCookie`), not just a presence check. Matcher excludes `/login`, `/api/*` (redirects make no sense for `fetch` calls — API routes self-verify and 401 instead), and static/PWA assets.
- **`app/api/session/route.ts`** — `POST` exchanges a fresh ID token for an httpOnly session cookie (`createSessionCookie`, 14-day max); `DELETE` clears it. `lib/session-cookie.ts` holds just the cookie name, shared with `proxy.ts` — kept dependency-free so importing it into `proxy.ts` never pulls `firebase-admin` into that Node-runtime-but-still-separate bundle.
- **`app/login/page.tsx`** — the one page `proxy.ts` never gates. Signs in, posts the ID token to `/api/session`, runs `lib/migrate-local-data.ts` (only does real work on a genuine first sign-in — see below), then navigates to `/`.
- **`app/api/define/route.ts`** verifies the session cookie itself (independent of `proxy.ts`, whose matcher excludes `/api/*`) and uses the resulting `uid` for both authorization and the per-user rate limit (`lib/rate-limit.ts`, rekeyed from IP to `uid`).
- **Data model**: one Firestore doc per user, `users/{uid}`, fields `{ favorites, history, srsCards, targetLanguage, lastStudyDeck }` — owner-only per `firestore.rules`. `favorites` is the field name, kept as-is for compatibility even though every user-facing surface calls this "Saved" now (`usePersistedList("favorites")`'s `field` param is the real Firestore key, not just a label). `lib/use-user-doc.ts` is the shared, module-level `onSnapshot` subscription `lib/use-persisted-list.ts`, `lib/use-srs-cards.ts`, `lib/use-target-language.ts`, and `lib/use-last-study-deck.ts` all build on (one Firestore listener per signed-in user, not one per hook) — the first two kept their pre-existing exported names/shapes when they moved off `localStorage`, gaining only an `isLoading` flag.
- **`lib/migrate-local-data.ts`** — one-time local→cloud migration, called from the login page. Only writes anything if the user's Firestore doc doesn't exist yet (a genuine first sign-in); never overwrites real cloud data.
- **`lib/use-last-study-deck.ts`** — `{ lastStudyDeck, setLastStudyDeck, isLoading }`, same `lib/use-user-doc.ts`-backed pattern as the hooks above. `components/study-flashcards.tsx` falls back to this (persisted, defaulting to `SAVED_DECK_ID = "saved"`) whenever `/study` has no `?deck=` in the URL, and writes to it whenever an explicit `?deck=` visit differs from the stored value — "last chosen deck," recorded regardless of entry point. `"saved"` is a virtual deck id standing in for the user's own saved words (`app/library/page.tsx` prepends a synthetic `{ id: "saved", ... }` entry to its real `useDecks()` list so it's reachable the same way any other deck is), keeping today's uncapped fetch-then-filter-by-due behavior — `lib/deck-study.ts`'s `selectWordsToStudy` cap stays specific to large pre-loaded decks.

### AI dictionary feature

- **`lib/gemini.ts`** — the only module that talks to Gemini. Owns the `GoogleGenAI` client, the structured-output `responseSchema` (`{ found, word, message, entries: [{ partOfSpeech, definition, example }] }`), and `normalizeWord()`/`InvalidWordError` for input validation. Model id is `GEMINI_MODEL` env var, defaulting to a hardcoded id — Gemini's flash-lite model naming moves fast, so re-check https://ai.google.dev/gemini-api/docs/models if lookups start failing. `DefinitionEntry`'s `translations` field is the one exception — always `[]` straight out of this module; it's populated downstream by `lib/translate.ts`, not by Gemini.
- **`lib/languages.ts`** — the curated list of bilingual-translation target languages (`SUPPORTED_LANGUAGES`, `DEFAULT_TARGET_LANGUAGE` = `"en"`, `isSupportedLanguage()`). Deliberately dependency-free (no `@google-cloud/translate` import) so client code (`lib/use-target-language.ts`, `app/settings/page.tsx`) can import it without pulling that package's Node-only transitive deps (grpc-js etc.) into the browser bundle — same rationale as `lib/session-cookie.ts` keeping `firebase-admin` out of `proxy.ts`'s bundle. Learned the hard way: putting these constants in `lib/translate.ts` itself broke the client build with `Module not found: child_process/fs/net/tls/http2/dns` once a client hook imported from it.
- **`lib/translate.ts`** — the only module that talks to the Google Cloud Translation API. `translateEntries(word, entries, targetLanguage)` batches all of a word's senses into one Translate API request for a single target language (the caller's per-user preference, not a fixed list — see `lib/languages.ts`) rather than one request per sense. `targetLanguage === "en"` short-circuits to no API call (English is the dictionary's own source language, so "translating" into it is a no-op — this is also the default for anyone who hasn't picked another language in Settings). Input to the API is `"${word} - ${definition}"`; the translated string is split back into `word`/`meaning` on the first surviving dash separator. Never throws — a missing `GOOGLE_TRANSLATE_API_KEY` or a failed request just means no translation for that word right now, since this is an enhancement on top of the core lookup, not a requirement for it.
- **`lib/firebase-admin.ts`** — singleton Firebase Admin app + Firestore instance (guarded against Next dev hot-reload double-init via `getApps()[0]`). Explicitly resolves a project id from `GOOGLE_CLOUD_PROJECT`/`GCLOUD_PROJECT` for local dev (user ADC credentials don't carry one, unlike a service account); on Firebase App Hosting both credentials and project id are auto-provided at runtime and this resolution is skipped.
- **`lib/definitions-cache.ts`** — the read-through cache in front of Gemini (+ Translation). `getDefinition(rawWord, uid, targetLanguage = "en")` normalizes the word, checks the `definitions/{normalizedWord}` Firestore doc, and on a miss calls `lib/gemini.ts`, then `lib/translate.ts`'s `translateEntries()` for just `targetLanguage` (via `attachTranslations()`, itself never throwing), then writes the combined result back (a cache-write failure is logged, never surfaces to the caller). Both "found" and "not found" results are cached, so repeated gibberish isn't re-billed either. Each cached entry's `translations` array is a **lang-keyed accumulator**, not a fixed set — it grows over time as different users request different languages for the same word. On a **hit**, `backfillTranslations()` translates and persists `targetLanguage` for any entry that doesn't have it yet (seeded/legacy docs from before Translate existed, or simply the first time anyone's asked for that particular language) — a one-time-per-(word, language) fix-up, not gated by the rate limit below since it never touches Gemini. An unrecognized `targetLanguage` (see `lib/languages.ts`'s `isSupportedLanguage()`) falls back to `"en"` rather than growing the cache with garbage. Concurrent requests for the same word (and, on the backfill path, the same language) are coalesced (`coalesce()`) so React Strict Mode's dev double-invoke, or two real near-simultaneous requests, only do the expensive work once. This is the only module that touches Firestore directly — `firestore.rules` denies all client read/write, since only the server-side Admin SDK ever reads this collection.
- **`app/api/define/route.ts`** — `GET ?word=&lang=` wrapping `getDefinition()`; `lang` is optional and client-supplied (same trust level as `word` itself — no server-side read of the caller's Settings preference). 400 for empty/invalid input, 502 for upstream (Gemini/Firestore) failures.
- **`lib/use-target-language.ts`** — the signed-in user's target-language preference (`{ targetLanguage, setTargetLanguage, isLoading }`), same `lib/use-user-doc.ts`-backed pattern as `lib/use-persisted-list.ts`. Consumers append `&lang=${targetLanguage}` to their `/api/define` fetch and gate that fetch's effect on `!isLoading` first — firing once with the pre-load `"en"` default and again once the real preference arrives would double the Gemini/Translate cost per lookup, so `components/word-detail.tsx`'s fetch effect waits for this to resolve before firing at all (unlike e.g. `addToHistory`, which is read through a ref specifically to *avoid* being an effect dependency — the two hooks need opposite treatment here since one's value changing should trigger a re-fetch and the other's shouldn't).
- **`app/settings/page.tsx`** — the target-language picker (shadcn `Select`, added via the CLI since none existed before this feature) sits above the account block, backed by `lib/use-target-language.ts` and `lib/languages.ts`'s `SUPPORTED_LANGUAGES`. Changing it persists immediately, no separate save step.
- **`components/dictionary-search.tsx`** — Home's search box + Recent Lookups only; it doesn't render lookup results itself. Submitting a search or picking a recent word navigates to `/word/[word]` (`components/word-detail.tsx`), which owns the actual lookup and every one of its states (loading, found, not-found, error).
- **Env vars** (no `.env.example` exists in the repo — the harness blocks writes to any `.env*` path, so this list is the source of truth): `GEMINI_API_KEY`, `GEMINI_MODEL`, `GOOGLE_TRANSLATE_API_KEY` (optional), the six `NEXT_PUBLIC_FIREBASE_*` client config values (required — see Authentication above), and for local dev either `GOOGLE_APPLICATION_CREDENTIALS` (service account JSON) or `gcloud auth application-default login` plus `GOOGLE_CLOUD_PROJECT`. See `README.md` for the full setup flow. (The bilingual-translation target language is a per-user Settings choice, not env config — see `lib/use-target-language.ts` above.)
- **Firebase deployment config**: `apphosting.yaml` (App Hosting run config + env/secret bindings — includes `REPLACE-ME` placeholders for the `NEXT_PUBLIC_FIREBASE_*` values, since those are real per-project config an agent can't obtain), `firebase.json` (App Hosting + Firestore config pointers), `.firebaserc` (project id, `lexi-gemini`), `firestore.rules` (owner-only for `users/{userId}`, deny-all for everything else), `firestore.indexes.json` (empty — all lookups are single-doc-by-ID). The backend (`lexi`) is connected to this repo on GitHub — pushing to `main` triggers an automatic build/rollout; `firebase deploy --only apphosting` is only needed for an out-of-band deploy. **`firestore.rules` changes are not part of that rollout** — deploy those explicitly with `firebase deploy --only firestore:rules`. Secrets (`GEMINI_API_KEY`, `GOOGLE_TRANSLATE_API_KEY`) are separate from the GitHub-triggered build — see `README.md`'s Deploy section.

### UI component system (shadcn/ui)

- `components.json` drives everything: style `base-maia`, base color `mist`, Tailwind CSS v4 (`cssVariables: true`), icon library `lucide`. Path aliases: `@/components`, `@/components/ui`, `@/lib`, `@/hooks` (all resolve via the single `@/*` tsconfig path).
- **Primitive library is Base UI (`@base-ui/react`), not Radix.** Existing shadcn/Radix knowledge for prop APIs (`asChild` vs `render`, event handling, etc.) doesn't directly transfer — check `.agents/skills/shadcn/rules/base-vs-radix.md` before assuming an API.
- Theme tokens (colors, radius, sidebar/chart colors) are CSS variables defined in `app/globals.css` under `:root` / `.dark`, remapped into Tailwind via the `@theme inline` block. `--radius` is the single source for all corner-radius scale steps (`--radius-sm` … `--radius-4xl` are derived from it). Edit `app/globals.css` for any theme/token change — never hand-roll a second config file.
- Installed components: `button`, `field`, `input`, `input-group`, `skeleton`, `empty`, `badge`, `card`, `alert`, `spinner`, `label`, `separator`, `textarea`, `select`. Use the shadcn CLI (`npx shadcn@latest add <component>`) to add more rather than hand-writing primitives; the project's shadcn skill (`.agents/skills/shadcn/`) has the full ruleset (forms use `FieldGroup`/`Field`, semantic color tokens only, `gap-*` not `space-y-*`, icons via `data-icon`, etc.) — follow it for any UI work.
- `lib/utils.ts` exports `cn()` (`clsx` + `tailwind-merge`) — the standard way to compose/override Tailwind classes across this codebase.

### Fonts

`app/layout.tsx` loads four `next/font/google` fonts (Geist, Geist Mono, Figtree as `--font-sans`, Outfit as `--font-heading`) and applies them as CSS variables on `<html>` via `cn()`. `globals.css` maps `--font-sans`/`--font-mono`/`--font-heading` into Tailwind's theme, so use the `font-sans`/`font-mono`/`font-heading` utility classes rather than referencing font variables directly.
